도커 네트워크

가상 네트워크

컨테이너 가상화: 서버 한대를 여러 컨테이너로 격리
가상네트워크: 서버 한대 안에서 여러 네트워크 구성

도커를 설치하고 실행하면 가상의 네트워크인 브릿지 네트워크, 가상의 공유기인 docker0를 만듬
가상의 공유기 docker0를 도커에서는 브릿지라고 부름
브릿지는 가상의 IP주소를 할당받음. 일반적으로 172.17.0.1
도커의 브릿지 네트워크는 컨테이너들에게 IP를 할당해주고 컨테이너들간에 통신할 수 있도록 만듬
도커에서 컨테이너를 실행하면 도커는 브릿지 네트워크의 IP 주소 범위 안에서 IP 주소를 하나 할당해줌
마치 공유기에 연결된 기기 한 대에 사설 IP가 할당되는 것과 동일
컨테이너를 추가 실행하면 각각의 컨테이너들은 같은 대역대에서 겹치지 않는 IP를 할당받음
같은 브릿지에서 생성된 네트워크는 브릿지를 통해서 서로 통신
-> 브릿지를 통해 네트워크 패킷을 전달

가상 인터페이스

물리 네트워크 인터페이스에 인터넷 선을 연결하면 기기의 공인 IP나 사설 IP를 할당받음
이 PC 위에서 도커를 설치하고 실행하면 도커는 가상의 인터페이스 한 개를 생성
이 가상의 인터페이스는 호스트 OS 위에 만들어짐
다음으로 컨테이너들을 실행할 때 각각의 컨테이너에 해당하는 가상 인터페이스들이
Veth라는 접두어로 호스트 OS에 만들어짐. Veth 뒤에는 랜덤한 고유 번호가 할당됨
가상의 인터페이스로 전달되는 네트워크 신호는 각각의 인터페이스에 해당되는 컨테이너로 전달됨

물리네트워크에서는 도착지의 IP에 맞게 네트워크를 통해서 기기에 전달하는 것을
네트워크 장비들이 알아서 해줌

가상네트워크에서는 별도의 장비가 없기 때문에 소프트웨어적으로 트래픽을 전달해줘야 함
가상의 인터페이스 간의 네트워크 패킷을 전달하는 규칙은 호스트 OS의 커널 소프트웨어인
IP Tables에 정의됨. IP Tables: Linux OS의 패킷 필터링 시스템
예시: Veth1에서 발생한 네트워크 요청이 17217.0.3을 도착지로 하고있고
iptables의 규칙에 따라서 Veth2로 전될되고 Veth2 인터페이스를 통해서 컨테이너 2로 전달됨
-> 도커는 컨테이너가 생성되거나 삭제될 때마다 호스트 OS의 iptables 규칙을 업데이트함
그리고 호스트 OS의 iptables 규칙을 관리하면서 가상 인터페이스들 간의 통신 규칙을 만듬
그래서 사용자는 별도의 설정을 하지 않아도 같은 브리지 네트워크 생성된 컨테이너들은
서로 통신을 할 수 있는 상태로 구성됨

도커는 가상네트워크 내부에서 여러 개의 브릿지 네트워크를 관리할 수 있음
기본적으로 같은 네트워크 안에 속해 있는 컨테이너들끼리는 통신이 가능
브릿지 네트워크 단위로 분리하게 되면 특정 컨테이너들끼리는 통신이 되지 않도록 구성할 수도 있음

포트포워딩 

1

docker run -p [HostOS의포트:컨테이너의포트]

각각 실행 중인 nginx 컨테이너와 데이터베이스 컨테이너는 바깥쪽에 있는
192.168.0.20이나 192.168.0.30 서버로 네트워크 신호를 보낼 수 있음
NAT는 가상 네트워크가 알아서 설정하기 때문에 특별히 지정하지 않아도 내부의 컨테이너는
이 바깥쪽에 있는 외부망을 통해서 다른 서버로 접근할 수 있음

외부의 서버에서 컨테이너로 접근할 때는 도커가 실행 중인 192.168.0.10를 통해서 접근해야함
여기서 포트 포워딩을 사용해 192.168.0.10의 특정 포트로 접근했을때 사용자가 지정한 컨테이너로
전달하도록 포트 포워딩을 등록해야함
예시: 172.17.0.2 서버의 타겟 포트를 80으로 지정하고 PC의 IP인 192.168.0.10의 8001번으로
요청을 보내면 nginx 컨테이너의 80 포트로 요청을 전달
-> 포트포워딩 기술을 사용하면 컨테이너 간 통신 뿐 아니라 컨테이너가 소속된 호스트 OS의 네트워크에서도
컨테이너로 접근할 수 있음

도커의 네트워크 드라이버

도커가 지원하는 네트워크 종류. 대부분 bridge 네트워크를 사용

브릿지 네트워크(Bridge): 도커 브릿지를 활용해 컨테이너간 통신, NAT 및 포트포워딩 기술을 활용해 외부 통신 지원

호스트 네트워크(Host): 호스트의 네트워크를 공유, 모든 컨테이너는 호스트 머신과 동일한 IP를 사용, 포트 중복 불가능

오버레이 네트워크(Overlay): Kubernetes에서 사용, 호스트 머신이 다수일 때 네트워크 관리 기술
여러 개의 호스트 머신이 있을 때, 이 여러 개의 호스트 머신들을 하나의 네트워크처럼 동작하게 만들어줌

Macvlan 네트워크: 컨테이너에 MAC 주소를 할당해 물리 네트워크 인터페이스에 직접 연결

스토리지와 볼륨

컨테이너의 상태

도커 볼륨

컨테이너는 stateless하기 때문에 컨테이너가 삭제되거나 재시작되면 모든 데이터가 이미지의 상태로 초기화됨
그런데 서버를 운영하다 보면 데이터를 유지해야 하는 경우가 있음(e.g. 데이터베이스)
유지한다는 것은 IT환경에서 영속성(Persistence)이 있다고 표현함

일반적으로 컨테이너를 운영하는 환경에서는 같은 역할을 하는 서버가 여러개로 운영됨(서버가 이중화 되어있음)
이때, 영속성이 필요한 데이터는 같은 종류의 모든 컨테이너가 함께 공유하고 있어야 함
예시: 로드밸런싱으로 3개의 db 컨테이너 1, 2, 3으로 트래픽을 분배할 때,
컨테이너 1에선 가격이 10000원, 컨테이너 3에서는 가격이 20000원으로 나오면 안됨

도커는 영속성이 필요한 데이터를 위해서 Docker 볼륨이라는 기능을 제공
컨테이너 자체는 상태를 가지지 않지만 상태가 필요한 데이터는 외부 공유 저장소에 저장해 두는 것
컨테이너의 특정 폴더를 공유용 폴더로 만들 수 있음 -> 컨테이너의 폴더를 볼륨에 마운트 한다고 표현
마운트: 컴퓨터의 특정 디렉토리를 외부 저장소로 대체한다는 것을 의미

USB를 PC에 연결하면 새로운 드라이브가 만들어짐
이 USB를 사용해서 데이터를 저장해 둘 수도 있고 다른 PC와 데이터를 공유할 수도 있음
이 USB와 동일한 역할을 하는 것이 네트워크 파일 시스템(NFS)
NFS를 사용하면 네트워크에만 연결되어 있으면 USB와 동일하게 데이터를 외부에 저장할 수 있음
한 번에 한 대만 연결 가능한 USB와는 다르게 네트워크 파일 시스템에는 동시에 많은 PC를 연결할 수 있음
NFS는 PC의 특정 폴더를 이 NFS에 마운트 시킬 수 있음. 스토리지의 종류에 따라서 마운트 되는 단위가 달라짐
연결할 때마다 새로운 드라이브가 추가되는 것처럼 드라이브 단위로 마운트가 될 수도 있고,
특정한 디렉토리만 마운트 시킬 수도 있음
-> 도커 볼륨은 USB처럼 데이터를 외부에 보관하는 기능을 제공
컨테이너들은 이 도커 볼륨을 컨테이너의 특정 경로에 마운트해서 사용
예시: postgresql 데이터베이스 컨테이너를 실행하면 컨테이너 안에 /var/lib/postgresql/data라는 폴더에
실제 데이터가 저장되는데 이 경로를 도커의 볼륨에 마운트하면 컨테이너가 실행된 다음에 이 경로에 저장하는 파일들은
컨테이너 레이어에 저장되는 것이 아니라 마운트되어 있는 외부 볼륨에 저장되어 있는 것
그리고 볼륨은 1개이고 컨테이너는 3개인데 1개의 볼륨을 3개의 컨테이너가 모두 동일한 경로에 마운트했기 때문에
모든 컨테이너는 동일한 데이터를 제공할 수 있음

# 컨테이너의 읽기/쓰기 레이어는 모두 삭제가 되지만 볼륨은 도커가 별도로 관리하기 때문에 그대로 남아있음
# 이 볼륨을 업그레이드되거나 재생성된 컨테이너가 다시 동일한 경로에 마운트하면
# 이전 볼륨에 만들어져 있던 데이터를 그대로 유지할 수 있음

바인드 마운트(Bind Mount)

볼륨을 마운트할때 실제 데이터를 호스트 OS의 데이터가 저장되는 경로는 volumes인데
예시
/volumes/volume1
/volumes/volume2
도커가 경로를 자동으로 관리하고 도커가 실행되는 가상 머신 안에서 저장되기 때문에
이 볼륨이 저장되는 경로에 사용자가 직접 접근하기는 어려움
HostOS에서 데이터를 직접 다루고 싶을 경우 바인드 마운트기능을 사용하면 됨
Bind Mount 기능을 사용하면 호스트 OS의 경로를 직접 지정할 수 있음
