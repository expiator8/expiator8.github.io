Docker with FastAPI 개발 환경 전략

Docker을 활용해 FastAPI 웹 애플리케이션 개발 환경 등을 손쉽고 일관되게 유지하기

Feb 06, 2025
6 minute read

개요(Instroduction)

도커 사용 목적 및 계기


개발자 각각 개인의 로컬 환경 또는 개발 환경, 운영 환경을 설정할 때 복잡하고 번거로운 작업을 해야했습니다.
물론 숙달이 되면 빠르게 작업할 수 있었지만 그렇다고 복잡하고 번거로운 작업이 줄어드는 것은 아니고
휴먼에러, 예상치 못한 에러가 발생하는 상황도 있었습니다.

새롭게 배포된 애플리케이션에서 문제가 발생했을 때 “내 PC에서는 잘 동작하는데”
이렇게 우기는 상황을 풍자한 유행어와 밈도 사용되는걸 볼 수 있는데

개발자의 PC마다 설치된 언어 및 라이브러리 버전을 일치시키기 위해,
여러 프로젝트를 개발할 경우에 여러 개의 환경을 어려움 없이 관리하기 위해,
이렇게 환경의 차이에서 발생하는 문제들을 근본적으로 해결해 업무 프로세스를 보다 효율적으로 만들기 위해.
컨테이너 플랫폼 도커를 활용해 로컬 환경, 개발 환경 및 운영 환경 등을 보다 손쉽고 일관되게 유지하기 위한 방법을 정리했습니다.

엔터프라이즈 웹 애플리케이션은 세 가지 종류의 서버로 구성했습니다.

  • 프론트엔드 소스를 제공하는 웹 서버
  • 비즈니스 로직을 수행하는 웹 애플리케이션 서버
  • 데이터를 저장하는 데이터베이스 서버

백엔드 애플리케이션에 대한 요청은 웹서버를 통해서만 접근이 가능합니다.
웹서버는 클라이언트와 백엔드 애플리케이션의 다리 역할을 하기 위해 프록시 기술을 활용합니다.

환경별 Docker 구성

로컬서버(Local Server)

VSCode나 IntelliJ IDEA에서는 원격 개발 환경 구성을 통해서 컨테이너 내부에서 개발할 수 있는 기능을 제공합니다.
컨테이너 안에서 소스 코드를 개발하면 개발자의 PC에서는 도커 외에는 아무것도 설치하지 않고도 코드를 개발할 수 있습니다.

IntelliJ의 원격 개발환경 구성 기능은 정식 라이선스로(유료)만 사용이 가능하기 때문에 VSCode로 진행했습니다.

VSCode Extension으로 Docker와 Dev containers를 설치합니다.

ARG python=python:3.13.1-alpine

# 이미지를 생성
FROM ${python} AS builder-stage

# 필요한 패키지 설치
RUN apk add --no-cache postgresql-dev gcc musl-dev linux-headers && python -m venv /home/app/.venv

# 가상 환경을 기본 실행 경로로 설정
ENV PATH="/home/app/.venv/bin:$PATH"

# 빌드 컨텍스트에서 requirements.txt 파일을 복사
COPY requirements.txt .

# 애플리케이션 의존성 설치
RUN pip install --no-cache-dir -r requirements.txt

# 이미지를 생성
FROM ${python} AS runtime-stage

# builder-stage의 /home/app/.venv를 build-image의 /home/app/.venv로 복사
COPY --from=builder-stage /home/app/.venv /home/app/.venv

# 가상 환경을 기본 실행 경로로 설정
ENV PATH="/home/app/.venv/bin:$PATH"

# 작업 폴더를 /home/app로 설정(cd /home/app과 동일하다고 볼 수 있음)
WORKDIR /home/app

# 빌드 컨텍스트의 모든 파일을 build-image의 /home/app으로 복사
COPY . /home/app

FastAPI 웹 애플리케이션 서버에 필요한 python 이미지의 태그는 alpine 이미지를 사용했습니다.

# 이미지를 생성
FROM ${python} AS builder-stage

# 필요한 패키지 설치
RUN apk add --no-cache postgresql-dev gcc musl-dev linux-headers && python -m venv /home/app/.venv

# 가상 환경을 기본 실행 경로로 설정
ENV PATH="/home/app/.venv/bin:$PATH"

# 빌드 컨텍스트에서 requirements.txt 파일을 복사
COPY requirements.txt .

# 애플리케이션 의존성 설치
RUN pip install --no-cache-dir -r requirements.txt

멀티 스테이징 기법을 사용해 builder-stage와 runtime-stage를 분리합니다.
최종적으로 웹 애플리케이션 실행에 필요한 의존성만 설치된 이미지를 빌드함으로써
이미지의 크기를 줄일 수 있습니다.

builder-stage에서는 다음 패키지를 설치했습니다.

  • postgresql-dev: PostgreSQL 데이터베이스 개발 라이브러리
  • gcc: C 컴파일러
  • musl-dev: 경량 C 표준 라이브러리
  • linux-headers: 커널 헤더 파일

pip install을 할 때에는 –no-cache-dir 옵션을 통해 다운로드된 패키지의 캐시 파일을 저장하지 않도록 해서 이미지의 크기를 좀 더 줄일 수 있도록 설치합니다.

spring 이미지를 활용해서 멀티스테이징을 했을때 이미지 크기가 많이 나는걸 본 적 있는데
python에서도 이미지 크기 차이가 클까? 라고 생각했습니다. 생각보다 크기 차이가 큰 걸 확인할 수 있었습니다.
183.42 MB가 멀티스테이징을 적용한 이미지, 822.08 MB가 멀티스테이징을 적용하지 않고 빌드한 이미지입니다.

docker compose 기능으로 컨테이너를 실행하기 위한 docker-compose.yml 파일은 위와 같이 작성했습니다.

stdin_open, tty는 docker run 명령어를 사용했을때 -i (interactive)와 -t (tty)에 해당하는 옵션입니다.

depends_on을 활용해 postgres 컨테이너가 실행된 후에 app 컨테이너를 실행하도록 하고
postgresql의 데이터는 볼륨으로 관리하도록 구성했습니다.

개발 서버에서는 로컬 서버 환경을 구성하는 Dockerfile과 대부분 유사합니다. 한가지 차이점은
마지막 줄에 웹 애플리케이션을 바로 실행하도록 uvicorn 명령줄을 추가했습니다.

개발서버에서는 이미지를 빌드하지는 않고 이 Dockerfile 내용으로 빌드된 이미지를
도커 레지스트리에 올려놓고 개발서버에서는 이미지를 pull 받아 컨테이너를 실행합니다.

services:  
  shoecatch:
    build: ./
    image: shoecatch_was:test
    depends_on:
      - postgres
    ports:  
      - "8000:8000"
    restart: on-failure

  postgres:
    image: postgres:17-alpine
    volumes:
      - postgres_data:/var/lib/postgresql/data
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: 1234
      POSTGRES_DB: shoecatch_test

  nginx:
    image: nginx:1.21.4-alpine
    ports:
      - "80:80"
    depends_on:
      - shoecatch
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro

volumes:
  postgres_data:

restart: on-failure 옵션으로 컨테이너가 예상치 못한 이유로 종료되었을때 자동으로 재시작하도록 작성했습니다.
restart: always를 하면 어떤 이유로든 자동으로 재시작 합니다.
