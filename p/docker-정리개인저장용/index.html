… server: 사전적인 의미는 ‘서비스(service)를 제공하는 사람’

인터넷이 발전하게 되면서 의미가 확장
서비스를 제공하는 하드웨어 또는 소프트웨어를 포함하는 의미

하드웨어와 그 하드웨어에서 실행되는 소프트웨어까지 모두 포함하는 단어

하드웨어만 있을때도, 소프트웨어만 있을때도 서버라 부를때가 있기 때문에 문맥에 따라 파악 예시 “서버의 전원이 꺼졌습니다” -> 하드웨어 서버 “서버 설치 파일을 다운받았습니다” -> 소프트웨어 서버

서버는 어떤 요청에 대한 결과를 제공 서버에 요청을 하는 주체는 클라이언트 클라이언트가 서버에 요청을 보내면 물리적인 하드웨어를 통해서 소프트웨어로 전달되고 소프트웨어가 요청에 해당하는 실제 기능을 수행한 다음 클라이언트에게 응답

어떤 소프트웨어가 실행 중인지에 따라서 다양한 서버로 분류

엔터프라이즈 환경에서 많은 양의 서버를 운영하는 방법은 크게 3가지가 있음

  • 베어 메탈 일반적으로 컴퓨터를 구입하고 프로그램을 실행시키는 방식과 유사
    서버를 구입해 그 서버 위에 os를 설치하고 여러 개의 소프트웨어를 실행
    엔터프라이즈 환경에는 비효율적

가상화 기술을 활용한 서버 운영 방식에는 하이퍼바이저, 컨테이너방식이 있음 도커는 컨테이너를 다루는 기술

  • 하이퍼바이저

  • 컨테이너

가상화 기술이란

실제로 존재하는 컴퓨터가 아니지만 마치 존재하는 것처럼 만들어주는 기술 간단히 말해 하나의 컴퓨터에서 여러개의 컴퓨터를 실행할 수 있음 -> 한 대의 컴퓨터만 가지고도 마치 여러 대를 가진 것처럼 사용할 수 있음

즉, 가상화 기술은 물리적인 컴퓨팅 환경 내부에서 논리적인 컴퓨팅 환경을 만들 수 있는 기술

가상화 기술은 왜 사용하는가

예시
8Core/64GB 메모리의 성능 좋은 서버가 있을때
1Core/8GB 메모리를 사용하는 프로그램 4개를 사용한다면
총 4Core/32GB 메모리를 사용

이 프로그램들을 실행할 수 있는 방법은?

  • 컴퓨터에 하나의 os를 설치하고 4개의 프로그램을 실행 os가 사용하는 리소스도 1Core/8GB 메모리를 사용한다고 가정했을때 5Core/40GB 메모리를 사용
    하나의 프로그램에 에러가 발생하면 다른 프로그램에도 영향을 줄 위험이 있음
    하나의 프로그램에 사용량이 급증해 리소스를 모두 쓰게 된다면 나머지 프로그램도 정상적으로 동작하지 못할 위험이 있음

엔터프라이즈 환경에서는 운영중인 환경이 멈추는 건 큰 장애로 이어질 수 있기 때문에
소프트웨어를 하나의 os에 올리는 것은 피하는 것이 좋음

  • 가상화 기술 사용
    한 대의 컴퓨터에 여러 대의 논리적인 os 환경을 구축하고 사용자가 리소스를 직접 분배
    하나의 가상 os가 사용할 수 있는 리소스 최대값을 지정

os 갯수가 1->5개로 증가. 하나의 os에서 4개의 프로그램을 실행할때보다 총 리소스 사용량은 증가

하지만 논리적으로 격리되어있기 때문에
한 대의 프로그램에서 에러가 발생해도 다른 프로그램에 영향을 주지않고
프로그램 하나가 버그가 생겨 리소스 사용량이 급증해도 os 한 대의 사용량은 제한되어 있기 때문에 하나의 환경의 문제로 끝

각각의 소프트웨어는 여러 대의 컴퓨터를 사용하는 것처럼 안정적으로 실행할 수 있음
물리적으로는 한 대의 컴퓨터를 사용해서 경제적이면서도 사용자는 여러 대의 컴퓨터를 사용하는 것처럼
가상 환경을 사용해서 안전하게 소프트웨어를 운영할 수 있음

그럼 하드웨어를 여러 대 사용하면 되지 굳이 가상화 기술을 사용하는 이유는?

하드웨어의 성능은 빠르게 발전하는 동시에 하드웨어를 사용하는 소프트웨어의 크기는 상대적으로 감소하는 추세
기업 입장에서 낮은 사양의 컴퓨터 여러 대를 사용하는 것보다 높은 사양의 컴퓨터를 한 대 사용하는 것이
가격, 설치 공간, 설치 인력, 서버 운영, 하드웨어 사이즈나 배선 등 여러가지 면에서 경제적

하이퍼 바이저

컴퓨터에 설치되는 프로그램
하이퍼바이저를 사용해서 가상화 환경을 관리(가상 os를 만들거나 실행 및 종료)
스토리지 공간만 사용하다가 가상 환경을 실행하면 cpu와 메모리도 사용

하이퍼 바이저 동작 원리 프로세스가 실행되기 위해서는 cpu나 메모리 같은 리소스를 사용해야 함
프로세스가 하드웨어를 사용하기 위해서는 os를 통해서만 사용할 수 있음
os는 하드웨어를 사용하기 위해 커널이라는 도구가 설치되어 있음
웹 브라우저나 문서 편집 프로그램을 실행할 때도 실행되어있는 프로세스들은 os의 커널에 하드웨어 리소스를 요청 커널은 하드웨어에 사용 요청을 대신 전달해주는 시스템 콜이라는 표준이 정해져있음 프로세스들은 커널에 시스템 콜을 보내서 하드웨어의 자원을 사용

대표적인 os로 window, linux, macOS등이 있음
각각의 os는 다른 종류의 커널을 사용하기 때문에 시스템콜도 다름
만약 윈도우 호스트 os에서 게스트 os로 macOS나 리눅스를 실행하는 경우
게스트 os의 커널은 실제 물리적인 하드웨어가 없기 때문에 리소스를 사용하려면
호스트 os의 커널로 리소스 사용을 요청해야 함

호스트 os와 게스트 os가 종류가 다르면 호스트 os는 게스트 os에서 전달받은
시스템 콜을 처리할 수 없음

이때, 하이퍼바이저가 커널간의 통신을 지원
격리된 공간을 만들면서 호스트 os와 다른 종류의 게스트 os를 사용할 수 있음

하이퍼바이저를 많이 사용하는 케이스
윈도우os에서 리눅스 os를 사용 윈도우 os는 사용성이 뛰어나지만 한 대의 성능이 무겁고 라이센스 가격도 높음
메인 os는 윈도우로 유지하면서 실제로 프로그램을 실행시키는 서버 운영은 가벼운 리눅스 서버를 사용

대표적인 하이퍼바이저 테스트환경: virtualbox 엔터프라이즈: vmware, redhat

컨테이너

현대 애플리케이션 운영 환경에서 하이퍼바이저보다 상대적으로 더 선호
가볍고 빠르다는 핵심 장점

컨테이너 가상화는 리눅스 커널이 제공하는 LXC(Linux Containers)라는 자체 격리 기술에서 출발 LXC 기술을 사용하면 하이퍼바이저를 사용하지 않고도 커널의 자체 기능만 사용해 격리된 공간 만들기 가능
LXC 기술은 커널의 네임스페이스와 CGroups(control groups)라는 기능을 활용

네임스페이스
프로세스와 하드드라이브, 네트워크, 사용자, 호스트 네임처럼 리소스를 나누는 기준

CGroups
프로세스가 사용하는 메모리와 CPU, 하드디스크, 네트워크 밴드위스처럼 리소스의 사용량을 배분하는 기술

컨테이너는 LXC 기술을 사용해서 만들어진 각각의 격리된 공간
즉, 컨테이너 가상화는 하이퍼바이저 없이 커널의 자체 기술을 활용한 가상화

컨테이너 가상화 특징
모든 컨테이너는 호스트 os의 커널을 공유해서 사용 각각의 시스템콜들이 하이퍼바이저를 거쳐가지 않아도 됨
-> 요청이 거쳐가는 단계가 적어 상대적으로 오버헤드가 적음
-> 하드웨어 리소스 사용 요청이 더 효율적으로 이루어짐
-> 게스트 os의 독립적인 커널을 실행하는데 필요한 시간 자체가 없어짐. 빠른 부팅 속도

커널을 독립적으로 가지는 가상 머신이 보안 면에서는 더 뛰어나다고 볼 수 있음
컨테이너는 호스트 os의 커널을 공유하기 때문에 호스트 os와 다른 종류의 os는 실행할 수 없음

도커

커널이 자체적으로 제공하는 가상화 기술은 사용자가 직접 컨트롤하기 어려움 도커는 이를 편리하게 사용하기 위해 만들어진 소프트웨어
사용자는 도커를 통해 컨테이너를 만들고 운영할 수 있음

하이퍼바이저 방식에서 격리된 공간을 만드는 소프트웨어가 하이퍼바이저라는 소프트웨어이면
컨테이너 가상화에서 실제 격리를 수행하는 주체는 도커 소프트웨어가 아닌 커널 그 자체
도커는 커널의 가상화 기술을 활용할 수 있게 도와주는 보조 도구

도커와 같은 가상화 도구를 컨테이너 플랫폼이라고 함
컨테이너 플랫폼은 자체적으로 가지고 있는 컨테이너 엔진과 컨테이너 런타임으로 구성 컨테이너 엔진: 사용자의 요청을 받아서 컨테이너를 관리하는 역할
컨테이너 런타임: 직접 커널과 통신하면서 격리된 공간을 만드는 역할 runc: 도커가 지원하는 기본 컨테이너 런타임. 다른 런타임을 사용할 수도 있음

컨테이너 플랫폼에는 Podman이나 Containerd 같은 다른 소프트웨어도 있음. 도커가 현업에서도 높은 점유율

도커 아키텍처

클라이언트-서버 모델로 실행 사용자의 명령을 전달해주는 클라이언트와 컨테이너를 관리해주는 도커 데몬(서버)

도커 데몬

컨테이너를 관리하는 기능을 제공해주며 도커 D라고도 부름
보통 데몬이라고 이름이 붙은 소프트웨어는 서버에서 지속적으로 실행이 되는 소프트웨어를 의미
호스트 os에서 지속적으로 실행되면서 클라이언트의 요청에 따라 컨테이너를 관리
클라이언트가 호스트 os의 커널의 기능을 활용해서 컨테이너를 관리하는 기능을 사용할 수 있도록 API를 제공
도커 엔진에서 제공하는 API 문서

도커 CLI(Command Line Interface)

사용자가 작업에 직접 일일이 API를 파악하고 사용하려면 번거로움이 있어
도커에서는 Command Line 도구인 Docker CLI가 클라이언트에 제공됨
클라이언트가 명령어를 입력하면 이 명령어를 서버의 API 양식에 맞게 만들어 전달. 도커 데몬의 API와 쉽게 통신

도커 CLI의 동작 예시

컨테이너 목록을 조회하기 위해 docker ps라는 명령어를 입력하면
Docker CLI는 이 명령을 API 양식에 맞게 만들어서 Docker 데몬에 전달
Docker 데몬은 요청을 분석해서 커널을 통해 컨테이너 리스트를 불러오고 JSON 형태로 응답
CLI는 전달받은 응답을 사용자가 보기 편한 테이블 형태로 만들어서 화면에 표시

서버에서 프로그램은 어떻게 실행되는가?
먼저 하드웨어가 필요하고, 그 하드웨어에서 실행할 소프트웨어가 필요
소프트웨어는 Nginx 웹서버처럼 소프트웨어를 다운받아서 실행할 수도 있고 직접 개발한 애플리케이션을 실행할 수도 있음
그런데 소프트웨어는 소프트웨어 하나만 가지고는 실행할 수 없음
소프트웨어가 하드웨어의 자원을 사용할 수 있도록 필수 기능을 제공해주는 OS가 필요
일반적으로 스프트웨어는 특정 패키지나 라이브러리의 의존성을 가지고 있고 실행시키기 위해서 런타임 언어를 설치해야 하는 경우도 있음
예를 들어 자바로 개발된 애플리케이션은 OS에 자바 소프트웨어를 실행하기 위한 자바 런타임이 설치되어 있어야 함

정리하면 서버에서 프로그램을 실행하기 위해 소프트웨어적으로 필요한 3가지: 기본 OS, 프로그램 실행에 필요한 구성 요소, 실행시킬 프로그램

그런데 Nginx 웹서버를 컨테이너로 실행하면

어떻게 서버를 구성하는 과정 없이 한번에 Nginx 프로그램을 실행할 수 있는가? Nginx 이미지를 통해서 컨테이너를 실행했기 때문

이미지는 백업이나 스냅샷과 유사한데 압축파일의 사이즈가 아주 작아 인터넷으로 저장하기, 공유하기가 상대적으로 훨씬 수월

이미지 레지스트리

도커 이미지를 저장하기 위한 저장소
이미지를 다른 사람과 공유하거나 필요한 이미지를 다운 받을 수 있음
가장 많이 사용되는 Public Image Registry: Docker Hub

GitHub가 소스 코드를 저장하는 자장소라면, Docker Hub는 이미지를 공유하는 저장소 GitHub: 소스 코드만 저장 Docker Hub: 소스 코드로 만들어진 애플리케이션, 그 애플리케이션을 실행할 수 있는 환경이 모두 포함된 이미지를 저장

이미지 레지스트리 제품들이 공통적으로 제공하는 기능

  • 이미지 공유: 기본적인 이미지 업로드, 다운로드 기능
  • 이미지 검색: 필요한 이미지들을 검색
  • 이미지 버전 관리: 사용자는 특정 버전의 이미지를 지정해서 다운 가능
  • 보안: 원하는 사용자만 이미지를 다운받을 수 있도록 인증 처리, 권한 관리, 업로드된 이미지의 보안을 검증하는 기능
  • 파이프라인: DevOps 파이프라인 기능과 연계해서 이미지를 업로드했을 때 자동으로 배포할 수 있도록 연계, 알림 기능

이미지가 저장되는 공간

  • 도커가 설치되어 있는 호스트 머신의 로컬 스토리지
  • 온라인 스토리지
    • 퍼블릭 레지스트리. 예시: docker hub
    • 주로 기업에서 많이 사용하는 프라이빗 레지스트리
      • 직접 서버에 레지스트리를 설치해서 사용. 예시: HARBOR, docker private registry. -> 서버에 직접 설치해야함
      • 퍼블릭 클라우드 서비스를 사용. 예시: AWS ECR, Azure Container Registry(ACR). -> 돈내야함

    이전레이어와 비교해서 추가되거나 변경된 파일들이 다음 레이어로 저장

이미지 B를 만들때 nginx 소프트 버전과 nginx 설정을 이미지 A와 동일하게 설정하면

index.html 파일을 수정하는 마지막 레이어만 새롭게 추가 되어서 이미지 B가 완성

docker image history [이미지명] # 이미지의 레이어 이력 조회

정리
Layering: 각 레이어는 이전 레이어 위에 쌓이며, 여러 이미지 간에 공유될 수 있음
레이어 방식은 중복데이터를 최소화하고, 빌드 속도를 높이며, 저장소를 효율적으로 사용할 수 있게 해줌

Copy-on-Write(CoW)전략: 다음 레이어에서 이전 레이어의 특정 파일을 수정할 때, 해당 파일의 복사본을
만들어서 변경 사항을 적용. 원래 레이어는 수정되지 않고 그대로 유지

Immutable Layers(불변 레이어): 이미지의 각 레이어는 불변으로, 한 번 생성되면 변경되지 않음(해시로 암호화된 고유값을 가짐)
이미지의 일관정을 유지하고, 여러 컨테이너에서 안전하게 공유

Cashing(캐싱): 레이어를 캐시하여, 이미 빌드된 레이어를 재사용할 수 있음
빌드시간 단축, 같은 레이어를 사용하는 여러 이미지에서 효율적으로 작동

-> 개인이 인프라를 관리하면 인프라의 상태를 변경한 기록을 관리하기도 어려움

Docker는 Dockerfile이라는 소스코드를 사용해 인프라의 상태를 저장하는 이미지를 만들 수 있음

커밋 방식은 이미지를 만들 때마다 컨테이너를 실행해야 되고 사용자가 명령어를 직접 입력해야 함
커밋 하나당 이미지의 레이어 하나가 추가되기 때문에
여러개의 레이어를 추가하고 싶을 때는
여러 번의 커밋을 수행해야 함

빌드 방식은 컨테이너를 생성하고 커밋하는 것을 도커가 대신 수행
도커에게 어떤 작업을 수행할지를 코드로 작성한 것이 바로 도커 파일

이미지 빌드는 도커에서 가장 많이 사용되는 기능 중 하나
컨테이너 애플리케이션 개발에 있어서 가장 핵심 기능이라고 볼 수 있음

1

docker build -t [이미지명] [Dockerfile 경로] # 도커파일을 통해 이미지 빌드

기본 Dockerfile 지시어 

1
2
3

FROM [이미지명] # 베이스 이미지 지정
COPY [파일경로] [복사할경로] # 파일을 레이어에 복사
CMD ["명령어"] # 컨테이너 실행 시 명령어 지정
  • 보통 이미지를 빌드할 때 필요한 파일 시스템이 있는 이미지를 베이스 이미지로 지정하는 것이 좋음 e.g. Node.js 애플리케이션을 실행하려면 Node.js가 설치되어 있는 이미지를 베이스 이미지로 선택
    Java 애플리케이션을 실행하려면 Java 런타임이 설치된 이미지를 Base 이미지로 선택

빌드 컨텍스트(Build Context) 도커 데몬이 이미지를 빌드할 때 전달되는 폴더, 이 폴더 안에 도커 파일과 카피에 사용할 파일들이 모두 들어있어야 함
예시: docker build -t my-image . 에서 . 이 빌드 컨텍스트

.dockerignore 빌드 컨텍스트에 전달될 파일을 조절
빌드 컨텍스트로 지정한 디렉토리의 모든 파일과 폴더가 Docker 데몬으로 전송되기 때문에 빌드 컨텍스트에는 실제로 이미지 빌드에 필요한 파일들만 넣어놓는 것이 유리
.dockerignore을 통해 빌드 과정에서 필요한 리소스를 효율적으로 관리할 수 있고 이미지가 빌드되는 시간을 최소화

멀티 스테이지 빌드

도커 파일에서 두 개의 베이스 이미지를 활용하는 방법
보통 애플리케이션을 빌드하는 과정에서 만들어지는 파일들이 용량을 많이 차지하는데
이 파일들은 실제로 애플리케이션이 실행되는 데 사용되지 않기 때문에
빌드에 사용하는 이미지와 실행에 사용하는 이미지로 나누는 방법

멀티 스테이지 빌드를 잘 활용해 실제 애플리케이션이 실행되는 이미지의 크기를 줄일 수 있음

FROM maven:3.6-jdk-11

COPY pom.xml .
COPY COPY src ./src

RUN mvn clean package

# 빌드된 JAR 파일을 실행 환경으로 복사
RUN cp /app/target/*.jar ./app.jar

# 애플리케이션 실행
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]

# 첫번째 단계: 빌드 환경 설정
FROM maven:3.6 AS build
WORKDIR /app

# pom.xml과 src/ 디렉토리 복사
COPY pom.xml .
COPY COPY src ./src

# 애플리케이션 빌드
RUN mvn clean package

# 두번째 단계: 실행 환경 설정
FROM openjdk:11-jre-slim
WORKDIR /app

# 빌드 단계에서 생성된 JAR 파일 복사
COPY --from=build /app/target/*.jar ./app.jar
# 빌드 컨텍스트에 있는 파일을 가져오는 것이 아니라
# build라고 이름지어진 maven 스테이지에서 파일을 가져옴

# 애플리케이션 실행
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]
